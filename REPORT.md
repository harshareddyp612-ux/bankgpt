# Design write-up

## 1. Architecture

**Shape.** One Python process, synchronous, CLI-driven. Six packages with one-way dependencies: `surface` (perceive/act) <- `agent` (discover) and `replay` (execute) -> `artifact` (contract), with `policy`, `escalation` and `evidence` as cross-cutting services. No queues, no services, no database: artifacts are JSON files, evidence is a folder per run. This is deliberate - the brief rewards abstractions that *could* scale, not infrastructure that does.

**Key decisions and trade-offs.**

- *Perception is a numbered element list + screenshot, not raw DOM.* The surface enumerates visible interactive controls and readable cells with a computed role, accessible name, "near text" (the labelling table cell), table header/row context, geometry and an xpath. The model chooses by index; it never sees or writes selectors. Trade-off: the enumerator is heuristic JS; it is the one piece that changes per surface, which is exactly where we want the variability to live.
- *Playwright, headed.* Chosen for actionability waits, role/label locators, frame handling, and because a headed Chromium *is* the operator console for the handoff - the human uses the same window the automation used. Coordinates exist only as a last-resort locator, so the same artifact vocabulary works for a screenshot-driven surface.
- *Claude via the Anthropic SDK, one request per step.* Each turn is self-contained: goal, compact action history, feedback on the last action, the current screen. No growing transcript, so cost is linear in steps and the model always reasons from the current state. Sensitive parameters are typed as `{{tokens}}` and substituted locally, so secrets never enter the model context. Server-side refusal fallback is enabled by default.
- *Policy is one function called from both loops.* `Policy.evaluate(action, element, url, mode)` is the single gate for discovery and replay, so the two paths cannot drift in what they permit.
- *The mock target is intentionally hostile* (tables, `<font>`, no ids, generic classes, POST-redirect flows) and has cookie-scoped fault injection so every runtime condition in the brief can be reproduced on demand.

## 2. Artifact schema

An artifact is a **contract a calling agent can reason about**, not a step list. `cua/artifact/schema.py` (pydantic, `extra=forbid`, cross-field validation) has:

- `inputs`: typed parameters with `pattern`, `required`, `example`, and `sensitive` (never stored or logged; substituted at type time).
- `outputs`: typed values (`string|integer|number|currency|...`) each bound to the extract step that produces it. `tool_definition()` emits a function-calling schema so the catalog is one method away.
- `steps`: surface-neutral actions (`navigate|click|type|select|press|extract|wait`) with a `target` **Locator**, templated `input`, `expect` post-conditions, and a `risk` flag with the policy's reason.
- **Locator = ranked candidate list.** Each candidate has a `strategy` (`role`, `label`, `near_text`, `table_cell`, `placeholder`, `text`, `css`, `xpath`, `coords`), a strategy-specific `value`, a `confidence` and a `rationale`. The recorder drops candidates whose value *is* dynamic content (a balance) and templates parameter values inside the rest (e.g. an href). `recorded` keeps what the control looked like for drift diagnosis. Replay logs which candidate resolved, so "we are now resolving by xpath" is visible before it becomes "broken".
- `checkpoint`: conditions that must hold at the end (URL pattern + success text the model named on the proving screen).
- `outcomes`: **OutcomeDetector**s mapping page conditions (text/url regex, HTTP status, overlay text) to `business | recoverable | hard`, with a bounded `recovery` for recoverable ones and `escalate` for hard ones. They come from a per-vendor **app profile** (`profiles/cu_core.yaml`) merged at record time, so replay knows what "no such member" looks like even though the happy-path run never saw it.
- `target` identifies the *vendor app*, `tenant` optionally pins an institution/version and carries `step_overrides` (section 4). `version`, `approval` (`draft -> approved -> deprecated`), `created_from_run`, and free-text `notes` make it reviewable in a PR.

Why this shape: the two mistakes the brief warns about - conflating a business answer with a crash, and single brittle selectors - are impossible to make by accident, because the schema forces an outcome taxonomy and a candidate chain.

## 3. Determinism & error handling

**Determinism.** Replay imports nothing from `agent`; it sets `CUA_NO_LLM=1` and any LLM client constructor raises (tested). Every step: policy check -> resolve the locator by walking candidates in confidence order (two passes with a short pause; `coords` only if explicitly allowed) -> perform with Playwright's actionability waits -> **poll post-conditions while running detectors** -> run detectors once more on the "successful" screen (late dialogs, business pages that keep the URL). Post-conditions are derived by the recorder from what actually happened (URL changed -> generalized URL regex with parameter values replaced by `\d+`/`[^/]+`), and the checkpoint is verified before outputs are returned. Values are typed on the way out (`$4,512.78` -> `4512.78`).

**Runtime conditions, three classes.** *Business* (`MEMBER_NOT_FOUND`, `VALIDATION_ERROR`, `MEMBER_RESTRICTED`, ...) stops the run and returns `BUSINESS_OUTCOME` with the app's own text - exit code 2, not an error. *Recoverable* (`SYSTEM_NOTICE_DIALOG` -> click Dismiss; `APP_ERROR`/5xx -> reload once; generic `UNEXPECTED_OVERLAY` -> try a dismiss-style button) applies a bounded recovery and re-evaluates the step; exceeding `max_attempts` turns it into a hard failure. *Hard* (`SESSION_EXPIRED`, `ACCESS_DENIED`/403, `LOCATOR_NOT_FOUND`, `POSTCONDITION_FAILED`, `CHECKPOINT_FAILED`) stops with `failed_step`, `expected` (the candidates tried or the condition) and `observed` (URL, status, text) - after offering the live session to a human when the detector or failure is marked `escalate` and an operator is configured. Artifact detectors run before generic ones and business before hard, so a legitimate answer is never misreported. Slow loads are handled by the wait model itself (tested with a 4 s injected delay).

**Drift (secondary).** Locator fallback is the first line; the per-step `locator_used` in every result is the signal. A step that resolves via `xpath` where it used to resolve via `role` is a candidate for re-recording before it fails.

## 4. Heterogeneity & multi-tenant

**Surface seam.** `Surface` is an ABC with nine methods: `observe`, `try_candidate`, `perform`, `wait_for`, plus session/handoff hooks. The artifact and the replay engine only know the surface-neutral action and locator vocabularies. A *legacy web* surface with framesets is the same Playwright implementation with `frame_path` (already in the schema and the enumerator) pointing into the frame tree. A *desktop* surface would implement `observe()` from the OS accessibility tree (Windows UIA / macOS AX), `try_candidate()` for `role`, `label`, `near_text` (spatially adjacent static text) and `coords`, and `perform()` via OS input events; `css`/`xpath` candidates are simply skipped. The recorder, policy, detectors (text and overlay based), escalation and evidence do not change. What *does* change per surface is the enumeration heuristic and the `table_cell` implementation, which is why both live inside the surface package.

**Multi-tenant reuse.** Artifacts are recorded against a *vendor app* (`target.app_id`), not a tenant. Reuse across institutions running the same product works in three layers: (1) the **app profile** carries vendor-level knowledge (outcome wording, known interstitials) shared by all tenants; (2) locators are semantic first (`role`+name, labelling text, table headers) and structural last, so branding, CSS and layout changes usually do not reach the fallback chain; (3) `tenant.step_overrides` lets a tenant pin a different locator, wording or wait for individual steps without re-recording - a base artifact plus a small overlay per variant, applied by `effective_steps()`. **Drift detection** is the `locator_used` and `recoveries` telemetry per tenant per step: a tenant whose steps start resolving by `xpath`, or whose checkpoints fail, is flagged for a re-record or an override; `target.app_version` and `tenant.app_version` let you correlate with the vendor release. Not built: the override authoring tool and the telemetry store.

## 5. Escalation & handoff

**Detecting "stuck".** Discovery: an unchanged screen fingerprint (URL, text, form values) for four steps, repeated policy denials, or the model calling `request_help`. Replay: any hard failure or detector marked `escalate` (expired session, permission denied, locator not found, unresolvable overlay), and any **risky step that lacks approval** (a confirmation request, not a repair request).

**Control-transfer model.** `ControlChannel` is an explicit state machine: `AUTOMATION -> INTERVENTION_REQUESTED -> HUMAN_IN_CONTROL -> RESUMING -> AUTOMATION` (or `ABORTED`), with an owner field and validated transitions; every transition is an evidence event. Automation only acts in `AUTOMATION`. An `InterventionRequest` carries run, capability/version, step, reason code and text, URL, a screenshot path, how to reach the session (headed window, optional CDP endpoint) and suggested actions.

**Taking control of the live session.** The surface stays open; `begin_human_control()` installs a recorder in the page (clicks, changes with password values masked, submits, navigations). The operator acts in the same browser window. `end_human_control()` returns what they did, which is stored with the intervention. The `OperatorConsole` is minimal by design: a CLI console (prompt in the terminal, actions in the headed browser) and scripted stand-ins for tests and unattended evidence, clearly labelled `scripted:<name>`. `NoOperatorConsole` models unattended production: the request is still raised and recorded, then the run ends `ESCALATED_ABORTED` with full context - in production that request goes to a queue instead of a terminal.

**Handing back.** On `resume` the channel passes through `RESUMING`, a post-handoff screenshot is taken, and the engine re-verifies rather than assumes: detectors run again, and the step is marked `human` if its post-conditions now hold, otherwise it is retried (bounded). Evidence `06-replay-lookup-session-expired-handoff` shows the whole cycle; the same channel is used for risky-step confirmation in both discovery and replay. The real discovery run in `08-discovery-open_member_subaccount` also shows the model using the channel on its own judgement: it saw that the member already held identical sub-accounts and called `request_help` before creating another, which is the behaviour the guardrails are meant to encourage.

## 6. Safety

**Allowlist.** `policy/allowlist.yaml`: hosts, allowed and denied path patterns, allowed action types. Evaluated for every action in both modes, including the *target* of a navigation or a link click and the *current* page (if the app drifts off-allowlist, nothing further is allowed). The fault-injection endpoint is explicitly denied to the agent.

**Risky vs safe.** An action is risky if it *commits*: clicking a button whose accessible name matches commit patterns (open/submit/confirm/transfer/...), or clicking a button / pressing Enter on a route flagged risky. Links with the same words are safe (navigation is reversible). Discovery routes risky actions to the operator for confirmation; replay allows them unattended only when the artifact is `approved` **and** the caller passed `confirm_risky`, otherwise it asks an operator or stops. The step's `risk` and reason are in the artifact so a reviewer sees them before approving. Justification: in a bank back office the cost of an unwanted commit dwarfs the cost of a pause.

**Data.** Parameters marked `sensitive` are typed by token, substituted locally, masked as `[REDACTED:<name>]` in every log and never stored in the artifact. Pattern redaction (SSN, card, API keys, bearer tokens, `password=`) runs on every event, result message and artifact note. Human keystrokes into password fields are masked at capture. Limits: screenshots are not pixel-redacted (the mock shows masked SSNs, but a real app would not; the fix is per-field blanking driven by the enumerator's `type=password`/profile-declared PII fields, not done here); the model sees page text of a regulated screen by necessity (the discovery run is the one place the model is in the loop, and it should run under a data-processing agreement); and regex redaction is a backstop, not a guarantee.

## 7. Cuts

Left out deliberately, with the seam in place: a real operator web console (the CLI console and the `OperatorConsole` interface stand in); a desktop surface (interface and locator vocabulary ready, no implementation); frameset targets (schema and enumerator support frames, the mock app has none); per-tenant override authoring and drift telemetry storage (schema fields and result signals exist); pixel-level screenshot redaction; artifact re-recording / versioning workflow beyond `approve`; assisted single-step LLM fallback on replay; multi-run stability scoring. The stretch goal built is the **agent-facing catalog** (`cua catalog --json`, `cua invoke <name>`, JSON result contract).

Next, in order: (1) a queue-backed intervention channel with a small web operator surface, since that is the production shape of the handoff; (2) per-field screenshot redaction; (3) a second mock "tenant" variant of the same vendor app to prove the override mechanism end to end and drive the drift signal; (4) bounded assisted recovery: one policy-checked model step when a locator chain is exhausted, recorded as evidence and as a proposed artifact patch.
